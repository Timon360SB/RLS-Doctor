# 2. НАЗНАЧЕНИЕ ПРОЕКТА

## 2.1. Основная проблема

Разработчики PostgreSQL и Supabase регулярно сталкиваются с ошибками при работе с Row-Level Security.

Типичные ситуации:

1. Пользователь авторизован, но запрос возвращает пустой массив.
2. SQL-запрос успешно работает в административном SQL Editor, но не работает из приложения.
3. RLS-политика существует, однако данные остаются недоступными.
4. Пользователь получает данные, которые согласно требованиям приложения не должен видеть.
5. Приложение отправляет запрос с неожиданным контекстом авторизации.
6. Отсутствуют необходимые SQL-привилегии.
7. `auth.uid()` возвращает `NULL`.
8. Политики настроены правильно, но приложение использует неправильную роль или токен.
9. Разработчик не может отличить ошибку RLS от отсутствия подходящих данных.
10. Изменение политики исправляет одну операцию, но нарушает другую.

Для диагностики разработчику приходится самостоятельно изучать:

- HTTP-запросы;
- заголовки авторизации;
- состояние пользовательской сессии;
- JWT;
- SQL-привилегии;
- RLS-политики;
- серверные логи;
- результаты SQL-запросов.

RLS Doctor должен объединить эти сведения в понятный процесс диагностики.

## 2.2. Цель продукта

Разработать инструмент, который помогает ответить на вопрос:

**«Почему конкретный запрос моего приложения выполнился не так, как ожидалось?»**

Программа должна:

1. Получать диагностические сведения о запросе приложения.
2. Анализировать доступные сведения об авторизации.
3. Проверять конфигурацию PostgreSQL.
4. Воспроизводить запрос в контролируемом тестовом окружении.
5. Сравнивать фактический результат с ожидаемым.
6. Формировать отчёт о выявленных расхождениях.
7. Предлагать действия для дальнейшей диагностики.

Инструмент не должен утверждать, что установил причину ошибки, если имеющихся данных для этого недостаточно.

# 3. КОНКУРЕНТНОЕ ПОЗИЦИОНИРОВАНИЕ

При проектировании необходимо учитывать существующие решения.

## 3.1. pgrls

Существующий анализатор PostgreSQL RLS.

Реализует:

- статический анализ политик;
- обнаружение проблем безопасности;
- проверку прав;
- сравнение изменений;
- тестирование RLS;
- интеграции с CI/CD.

Необходимо изучить актуальную документацию и функциональность перед разработкой пересекающихся модулей.

## 3.2. rlsautotest

Существующий инструмент автоматической генерации тестов PostgreSQL RLS.

Реализует:

- анализ политик;
- генерацию тестовых данных;
- проверку доступа;
- создание pgTAP-тестов;
- интеграцию с Supabase;
- отчёты.

## 3.3. Supabase

Supabase предоставляет собственные средства работы с RLS, включая Security Advisor, инструменты тестирования и предварительную реализацию RLS Tester.

По состоянию на проведённое исследование, развитие предварительного RLS Tester было приостановлено для пересмотра направления.

Перед реализацией необходимо проверить актуальное состояние этих инструментов.

## 3.4. Наше отличие

RLS Doctor должен специализироваться на:

**Application Request Diagnostics + Controlled Reproduction + Authorization Analysis.**

Мы не пытаемся заменить pgrls или rlsautotest.

Основное преимущество, которое требуется проверить на практике:

Объединение диагностики запросов приложения с воспроизведением поведения авторизации в тестовом окружении.

Это продуктовая гипотеза, а не доказанное уникальное преимущество.

# 5. АРХИТЕКТУРА ПРОДУКТА

Проект должен состоять из двух основных подсистем и общего контракта обмена данными.

## 5.1. Подсистема A — Request Capture SDK

**Язык:** TypeScript.

Назначение:

Собирать безопасные диагностические метаданные HTTP-запросов Supabase-приложения.

Основная интеграция — через пользовательскую реализацию `fetch` в supabase-js.

SDK должен работать прозрачно для приложения:

- не изменять запросы;
- не изменять ответы;
- не нарушать работу авторизации;
- не влиять на бизнес-логику;
- не требовать изменения RLS-политик.

Первая версия должна поддерживать Node.js.

Поддержку браузерного окружения добавлять после проверки совместимости и модели безопасности.

## 5.2. Подсистема B — Diagnostic & Replay Engine

**Язык:** Python.

Назначение:

- Обрабатывать диагностические события.
- Проверять корректность их формата.
- Анализировать доступные сведения об авторизации.
- Подключаться к локальному PostgreSQL.
- Анализировать RLS-конфигурацию.
- Выполнять контролируемые запросы через локальный Supabase REST API.
- Проверять ожидаемые результаты.
- Формировать диагностические отчёты.

## 5.3. Общий контракт

Обе подсистемы должны использовать единую версионируемую JSON Schema.

Нельзя допускать ситуаций, когда изменение формата событий в TypeScript незаметно нарушает работу Python.

Изменения схемы необходимо проверять в CI.

# 6. ФУНКЦИОНАЛЬНЫЕ ТРЕБОВАНИЯ

## 6.1. Модуль Request Capture

**ID: RC-01 — Интеграция с supabase-js**

Реализовать обёртку над `fetch`, которую можно передать при создании Supabase-клиента.

Обёртка должна сохранять стандартное поведение Fetch API.

**ID: RC-02 — Захват диагностических событий**

Для поддерживаемых запросов необходимо получать:

- HTTP-метод.
- Тип обращения к API.
- Имя запрашиваемого ресурса, если его можно безопасно определить.
- HTTP-статус ответа.
- Время выполнения.
- Наличие заголовка Authorization.
- Наличие API-ключа без раскрытия его значения.
- Количество возвращённых записей, если это можно определить без чтения чувствительного содержимого.
- Код ошибки, если он доступен.
- Локальный идентификатор диагностического события.

**ID: RC-03 — Обработка чувствительных данных**

Запрещено записывать:

- Полные JWT.
- Refresh Tokens.
- Service Role Keys.
- Secret API Keys.
- Пароли.
- Cookies.
- Полные заголовки Authorization.
- Содержимое пользовательских таблиц.
- Необработанные тела HTTP-ответов.
- Значения чувствительных параметров запросов.

Должна использоваться модель минимального сбора данных.

Имена параметров и SQL-операторы можно сохранять только после безопасной нормализации.

**ID: RC-04 — Управление записью**

SDK должен иметь возможность:

- Включать диагностику.
- Выключать диагностику.
- Ограничивать список отслеживаемых запросов.
- Настраивать место сохранения отчётов.
- Ограничивать время и объём записи.

По умолчанию диагностика выключена.

**ID: RC-05 — Обработка ошибок**

Ошибка внутри RLS Doctor SDK не должна приводить к аварийному завершению основного приложения.

Ошибки диагностики должны фиксироваться отдельно от ошибок приложения.

---

## 6.2. Модуль Identity Diagnostics

**ID: ID-01 — Анализ контекста авторизации**

Необходимо различать:

- Ожидаемую роль.
- Роль, заявленную в диагностическом сценарии.
- Роль, подтверждённую в доверенном тестовом окружении.
- Неизвестную роль.

Наличие Authorization не доказывает успешную авторизацию.

Нельзя считать содержимое декодированного JWT подтверждённой личностью без проверки его подписи и необходимых claims.

**ID: ID-02 — Проверки**

Реализовать диагностику:

- Отсутствия ожидаемой пользовательской авторизации.
- Несоответствия фактического HTTP-статуса ожиданию.
- Неожиданного выполнения запроса в анонимном тестовом контексте.
- Отсутствия необходимого тестового контекста.
- Проблем доступа, связанных с проверяемой ролью PostgreSQL.

**ID: ID-03 — Степень достоверности**

Каждый диагностический вывод должен содержать статус доказательности:

`OBSERVED` — непосредственно наблюдаемый факт.

`INFERRED` — вывод, полученный из достоверных фактов, с указанием оснований и ограничений.

`UNVERIFIED` — гипотеза, требующая дополнительной проверки.

Не путать эти статусы со статусом прохождения теста.

---

## 6.3. Модуль PostgreSQL Inspector

**ID: PG-01 — Подключение**

Реализовать подключение к локальному PostgreSQL.

Использовать Psycopg 3.

Строки подключения получать из переменных окружения или конфигурации, не содержащей секретов.

**ID: PG-02 — Анализ конфигурации**

Получать:

- Сведения о таблице.
- Состояние RLS.
- Состояние FORCE ROW LEVEL SECURITY.
- Список RLS-политик.
- Операции, к которым применяются политики.
- Роли, указанные в политиках.
- Типы PERMISSIVE / RESTRICTIVE.
- Условия USING / WITH CHECK.
- Необходимые SQL-привилегии.
- Сведения о возможном обходе RLS.

Учитывать членство ролей и наследование привилегий.

**ID: PG-03 — Выводы**

Инструмент должен обнаруживать подтверждённые конфигурационные проблемы.

Например:

- RLS отключён.
- Для выбранной операции не существует применимой разрешающей политики.
- Отсутствует необходимый GRANT.
- Роль обходит RLS.
- Конфигурация содержит условия, требующие дополнительного пользовательского контекста.

Необходимо учитывать, что отсутствие подходящей строки в результате SELECT не доказывает фильтрацию со стороны RLS.

**ID: PG-04 — Ограничения анализа**

Нельзя обещать полную статическую интерпретацию произвольных SQL-функций.

Если для вывода недостаточно информации, возвращать `UNVERIFIED`.

Для первой версии модуль должен быть преимущественно средством чтения конфигурации, а не автоматическим исправителем политик.

## 6.4. Модуль Request Replay

**ID: RP-01 — Назначение**

Реализовать механизм воспроизведения GET-запросов Supabase REST API.

Запросы должны выполняться только в контролируемом локальном окружении.

**ID: RP-02 — Тестовые данные**

Использовать специально созданные тестовые данные.

Не переносить реальные пользовательские данные и production-токены.

**ID: RP-03 — Контекст**

Тестовое окружение должно поддерживать:

- Анонимные запросы.
- Запросы авторизованного тестового пользователя.
- Несколько тестовых пользователей.
- Проверку доступа к собственным и чужим записям.

Токены тестовых пользователей должны получаться через поддерживаемые механизмы локальной Supabase Auth либо передаваться безопасным способом из переменных окружения.

**ID: RP-04 — Повтор запроса**

Необходимо понимать ограничение безопасного сбора данных:

Обезличенное диагностическое событие не содержит всех значений оригинального HTTP-запроса.

Поэтому точное воспроизведение запроса только по событию не всегда возможно.

Для Replay пользователь должен явно задать необходимые фильтры и тестовые значения в локальном сценарии.

Это контролируемое воспроизведение поведения, а не автоматический повтор production-запроса с оригинальными секретами.

**ID: RP-05 — Допустимые операции MVP**

В первой версии поддерживать только:

`GET /rest/v1/...`

Операции POST, PATCH, PUT и DELETE не реализовывать в динамическом движке MVP.

**ID: RP-06 — Ограничения безопасности**

По умолчанию разрешать обращения только к локальным тестовым адресам.

Предусмотреть защиту от:

- Обращений к произвольным удалённым адресам.
- Подмены локального адреса через перенаправления.
- Использования production-токенов.
- Случайного запуска изменяющих запросов.
- Записи чувствительных данных в диагностические файлы.

Не полагаться исключительно на проверку строки `localhost`.

## 6.5. Модуль Result Comparison

**ID: CP-01 — Проверка ожиданий**

Поддерживать следующие проверки:

- Ожидаемый HTTP-статус.
- Ожидаемое количество строк.
- Ожидаемое наличие конкретной тестовой записи.
- Ожидаемое отсутствие чужой тестовой записи.
- Ожидаемый класс ошибки.

**ID: CP-02 — Результаты**

Каждая проверка должна возвращать:

`PASS` — ожидание подтверждено.

`FAIL` — обнаружено расхождение.

`UNKNOWN` — результат невозможно достоверно определить.

`ERROR` — проверка не завершена из-за ошибки окружения или исполнения.

**ID: CP-03 — Интерпретация**

Необходимо различать:

- HTTP-ошибку.
- Ошибку SQL-привилегий.
- Отсутствие подходящих записей.
- Фильтрацию строк RLS.
- Ошибку конфигурации тестового окружения.

Если нельзя достоверно различить эти ситуации, программа должна обозначить неопределённость.

# 7. ДИАГНОСТИЧЕСКИЕ ОТЧЁТЫ

Реализовать два формата:

1. Консольный отчёт.
2. JSON-отчёт.

HTML-интерфейс не входит в MVP.

## 7.1. Структура отчёта

Отчёт должен содержать:

- Идентификатор проверки.
- Дату выполнения.
- Проверяемый ресурс.
- Метод запроса.
- Ожидаемую роль.
- Подтверждённую тестовую роль.
- Результат HTTP-запроса.
- Результат PostgreSQL Inspector.
- Результаты проверок.
- Подтверждённые факты.
- Возможные причины.
- Рекомендации.
- Ограничения диагностики.

## 7.2. Пример результата

```text
RLS DOCTOR v0.1.0

Resource: public.documents
Operation: SELECT

Expected role:
  authenticated

Test environment:
  local Supabase

HTTP result:
  200 OK

Expected rows:
  1

Actual rows:
  0

RESULT: FAIL

CONFIRMED:
  - Request completed successfully.
  - Test user received zero rows.
  - RLS is enabled.

POSSIBLE CAUSES:
  - Policy predicate excluded the test row.
  - Test identity does not match the fixture.
  - Request filters excluded the expected row.

NEXT STEPS:
  1. Verify test user identity.
  2. Verify fixture ownership.
  3. Inspect applicable SELECT policies.
```

Этот формат является примером желаемого вывода.

Конкретные утверждения о применённых политиках должны появляться только при наличии достаточных диагностических данных.

`rls-doctor`

```bash
rls-doctor init
```

```bash
rls-doctor doctor
```

Проверяет:

- Наличие необходимой конфигурации.

- Возможность подключения к тестовому PostgreSQL.

```bash
rls-doctor inspect public.documents
```

Показывает доступные сведения о таблице, RLS и правах доступа.

```bash
rls-doctor replay scenarios/documents.yaml
```

Выполняет контролируемое воспроизведение запроса.

## 8.5. Формирование отчёта

```bash
rls-doctor replay scenarios/documents.yaml --format json
```

Формат JSON должен быть пригоден для программной обработки.

# 15. ОБЯЗАТЕЛЬНЫЕ ТЕСТОВЫЕ СЦЕНАРИИ

Для MVP подготовить автоматические проверки.

| ID | Сценарий | Что нужно проверить |
|---|---|---|
| T01 | Отсутствует авторизация | Корректная диагностика анонимного запроса |
| T02 | Авторизованный пользователь | Корректная обработка тестовой сессии |
| T03 | RLS отключён | Отображается подтверждённое состояние |
| T04 | Нет SELECT-политики | Определяется default-deny |
| T05 | Недостаточный GRANT | Обнаруживается отсутствие необходимого права |
| T06 | Неправильный пользователь | Запрос не получает чужую тестовую запись |

| T08 | Пустая таблица | Отсутствие данных не называется доказанной ошибкой RLS |

# 16. ТРЕБОВАНИЯ К БЕЗОПАСНОСТИ

Это один из важнейших разделов проекта.

RLS Doctor предназначен для анализа авторизации, поэтому безопасность должна закладываться в архитектуру.

## Обязательные ограничения

1. Не собирать JWT и пароли.
2. Не сохранять производственные секреты.
3. Не отправлять диагностические данные третьим лицам.
4. Не запускать изменяющие запросы в production.
5. Не подменять пользовательскую авторизацию в реальном приложении.
6. Не использовать production-данные для автоматических тестов.
7. Не предоставлять пользователю ложных гарантий безопасности.
8. Не считать клиентские JWT-claims подтверждёнными без надлежащей проверки.
9. Не выполнять произвольный SQL из диагностических файлов.
10. Не скрывать неопределённость результатов.

Для динамического тестирования использовать только явно разрешённую локальную среду.

Режим подключения к удалённым тестовым базам рассматривать исключительно после отдельного проектирования механизмов безопасности.

# 23. ГЛАВНЫЕ ПРИОРИТЕТЫ

При конфликте требований использовать следующий порядок:

**Приоритет №1 — безопасность**

Инструмент не должен создавать риск утечки данных или изменения рабочей базы.

**Приоритет №2 — достоверность**

Нельзя сообщать пользователю неподтверждённую причину ошибки как установленный факт.

**Приоритет №3 — работоспособность MVP**

Лучше небольшой реально работающий инструмент, чем большой набор незавершённых функций.

**Приоритет №4 — качество архитектуры**

Каждый компонент должен быть понятным и тестируемым.

**Приоритет №5 — удобство использования**

Пользователь должен быстро получить диагностическую информацию без изучения внутреннего устройства инструмента.

**Приоритет №6 — расширяемость**

Новые функции должны добавляться без переписывания всей системы.
