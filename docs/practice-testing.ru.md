# Полная проверка RLS Doctor на учебной базе

[English version](practice-testing.md)

Для уже подготовленной среды на этом компьютере есть [маршрут из 36 ручных проверок](manual-test-plan.ru.md), включая прямой экспорт JSON и мастер настройки.

Эта инструкция проверяет текущую версию продукта на настоящем локальном
Supabase: PostgreSQL, Auth, REST API и реальном запросе Node.js SDK.
Все документы и пользователи синтетические. Это учебная база для проверки
инструмента, а не подключение вашего рабочего приложения.

## 1. Что подготовлено

Запускатель: `lab.cmd` в корне репозитория. Он создаёт отдельный Docker-проект
`rls-doctor-practice`, не используя базу прежнего демо.

| Компонент | Адрес / назначение |
| --- | --- |
| API | `http://127.0.0.1:55321` |
| PostgreSQL | `127.0.0.1:55322` |
| Рабочие файлы базы | `.rls-doctor/practice/supabase/` |
| Сценарии и отчёты запуска | `.rls-doctor/practice/run-…/` |
| Язык по умолчанию | English; русский: `lab.cmd -Language ru` |

В Docker Desktop появятся контейнеры с окончанием `rls-doctor-practice`.
Учебные ключи не надо узнавать или копировать. Запускатель держит их в памяти,
а в файлы сохраняет только настройки, синтетические сценарии и очищенные отчёты.
Папка `.rls-doctor` исключена из Git.

Две тестовые личности условно называются **Алиса** и **Боб**. При каждом запуске
создаются новые Auth-пользователи с генерируемыми тестовыми логинами и паролями,
а восемь строк этой учебной базы назначаются новой паре пользователей.
Старые Auth-пользователи остаются до удаления/сброса локальной среды.

В каждой таблице по две синтетические строки:

| Документ | Условный владелец | Синтетический ID |
| --- | --- | --- |
| Lab: Alice project plan | Алиса | `10000000-0000-4000-8000-000000000001` |
| Lab: Bob project notes | Боб | `10000000-0000-4000-8000-000000000002` |

| Таблица | Настройка | Для чего нужна |
| --- | --- | --- |
| `documents` | SELECT разрешён, RLS ограничивает строки владельцем | Правильный доступ |
| `blocked_documents` | SELECT разрешён, разрешающей RLS-политики нет | Проверка запрета по умолчанию |
| `no_grant_documents` | RLS-политика есть, SELECT не выдан | Проверка SQL-привилегий |
| `leaky_documents` | SELECT разрешён, политика пропускает всех авторизованных | Намеренная ошибка изоляции |

Тестовая функция определения исполняемой роли установлена только в этой
контролируемой базе. Она не устанавливается автоматически в ваше приложение.

## 2. Как запустить

1. Откройте Docker Desktop и дождитесь готовности движка.
2. Откройте **новое окно PowerShell**.
3. Вставьте команду и нажмите Enter:

```powershell
cd C:\Users\sbtim\Documents\GitHub\RLS-Doctor
```

4. Вставьте следующую команду отдельно:

```powershell
.\lab.cmd
```

5. На вопрос `Prepare practice database? [y/n]` введите **y** и нажмите Enter.
6. Дождитесь сообщения `Ready` и меню `Choose a check`.

Во время подготовки запускаются зависимости, сборка SDK и отдельные контейнеры.
Первые минуты могут уйти на загрузку образов. Пока команда работает, повторно её
не запускайте. Дополнительное окно терминала не требуется.

Для русской версии вместо шага 4 выполните:

```powershell
.\lab.cmd -Language ru
```

Не запускайте две учебные сессии одновременно: они назначают владельцев одних
и тех же восьми строк. Прежнее демо использует другие порты и базу.

## 3. Как читать результаты

| Результат | Значение |
| --- | --- |
| PASS / 0 | Наблюдение соответствует ожиданию сценария |
| FAIL / 1 | Есть расхождение с ожиданием |
| UNKNOWN / 2 | Для подтверждения поведения недостаточно доказательств |
| ERROR / 3 | Проверка не выполнена или входные данные отклонены |

В отрицательных примерах **FAIL или ERROR — ожидаемый ответ**. Например, если
мы специально передали неверный токен, правильная работа продукта — отклонить
его, а не показать PASS. Под отчётом сверяйте `Expected / Actual` и `MATCH`.

`MATCH` означает, что учебный пример сработал именно так, как был задуман.
Это не общий вывод о безопасности приложения.

Факты и догадки показываются отдельно:

- `OBSERVED`: непосредственно наблюдалось.
- `INFERRED`: выведено из указанных фактов.
- `UNVERIFIED`: не установлено; требуется другая проверка.

## 4. Первый проход: связь, SDK и правильный доступ

В меню вводите **только номер**, затем Enter. После отчёта меню появится снова.

### Пункт 1 — Check connection

Проверяет локальный API, PostgreSQL, роли и доверенную проверку контекста.

**Ожидается:** PASS, код 0. Если здесь ошибка, остальные пункты пока не считайте
проверенными: проверьте Docker и завершение подготовки.

### Пункт 2 — Capture SDK request and validate

Настоящий `supabase-js` отправляет GET от Алисы. SDK создаёт очищенное событие,
а Python CLI проверяет его по общей JSON Schema.

**Ожидается:** PASS, код 0. В папке текущего `run-…` появится `event.json`.
В событии есть метаданные, но нет токена, пароля или содержимого строк.
Это проверка реальной цепочки приложение → SDK → событие → Python.

### Пункт 3 — Offline event analysis

SDK снова получает событие настоящего запроса. Затем CLI разбирает сохранённое
событие офлайн, без дополнительного воспроизведения или подключения к БД.

**Ожидается:** UNKNOWN, код 2. Наличие заголовка Authorization в событии не
доказывает личность и исполняемую роль. Это предусмотренное ограничение анализа.

### Пункт 4 — Alice: own row only

Проверяет не только число строк: документ Алисы должен присутствовать,
документ Боба — отсутствовать.

**Ожидается:** PASS / 0, HTTP 200, 1 строка, роль `authenticated`.
Проверки присутствия своей и отсутствия чужой записи должны пройти.

### Пункт 5 — Bob: own row only

Тот же запрос, но с другой тестовой личностью. Теперь доступна строка Боба,
а строка Алисы недоступна.

**Ожидается:** PASS / 0, HTTP 200, 1 строка. Это проверяет обе стороны изоляции,
а не только один удачный запрос.

## 5. Второй проход: обнаружение проблем

| Номер | Что выбрать | Что специально сделано | Ожидается |
| --- | --- | --- | --- |
| 6 | Missing authorization | Ожидаем авторизованный доступ, отправляем анонимный GET | FAIL / 1, HTTP 200, 0 строк, роль anon |
| 7 | No allowing policy | GRANT есть, но разрешающей SELECT-политики нет | FAIL / 1, HTTP 200, 0 строк |
| 8 | Expected SELECT denial | SELECT не выдан; сценарий ожидает отказ | PASS / 0, HTTP 403, класс permission |
| 9 | Detect another user's row | Намеренно неправильная политика раскрывает обе строки | FAIL / 1, HTTP 200, 2 строки, нарушена проверка исключения чужой записи |
| 10 | Nonexistent row ambiguity | Фильтр выбирает заведомо отсутствующую строку | PASS / 0, HTTP 200, 0 строк, EMPTY_RESULT_AMBIGUOUS / UNVERIFIED |
| 11 | Inspect missing privilege | Читаются права и RLS из каталогов, без запроса строк | UNKNOWN / 2 и SELECT_PRIVILEGE_MISSING |

**Что понять из пункта 8:** PASS может означать, что ожидаемый отказ подтвердился.
Политика RLS не выдаёт SQL-привилегии.

**Что понять из пункта 9:** продукт обнаружил чужую запись. FAIL здесь нужен,
чтобы инструмент не пропустил нарушение изоляции.

**Что понять из пункта 10:** такой же пустой ответ бывает и без блокировки RLS.
Инструмент должен сохранить неопределённость причины.

## 6. Третий проход: защитные отказы

| Номер | Проверка | Ожидаемый ответ |
| --- | --- | --- |
| 12 | Reject invalid token | ERROR / 3, INVALID_TEST_TOKEN; некорректный токен отклонён до чтения таблицы |
| 13 | Reject invalid event | ERROR / 3, INVALID_EVENT; неподдерживаемая версия события не принимается |
| 14 | Replay approval required | ERROR / 3, LOCAL_APPROVAL_REQUIRED; неутверждённая среда не используется |
| 15 | Reject remote address | ERROR / 3, UNSAFE_ENDPOINT; удалённый адрес не используется |
| 16 | Reject PATCH replay | ERROR / 3, INVALID_SCENARIO; запись через replay не допускается |

Исходные рабочие настройки не портятся: для этих проверок используются отдельные
отрицательные примеры. Не исправляйте их ради получения зелёного PASS.

## 7. Проверка новой команды session

1. В главном меню выберите **17 — Managed session menu**.
2. Появится меню самой команды session. Это другой уровень меню в том же окне.
3. Выберите **1 — Run scenario**. Ожидается PASS / 0 для доступа Алисы к своей строке.
4. Выберите **2 — Inspect table configuration**. Ожидается UNKNOWN / 2:
   каталог показывает настройки, но сам по себе не доказывает поведение запроса.
5. Выберите **0**. Вы вернётесь в главное учебное меню.

Ключи загружаются через CLI выбранного локального проекта. Тестовая личность уже
подготовлена учебным запускателем и передаётся дочерней команде в памяти.
Для этого пункта не требуется новая регистрация или копирование токена.

## 8. Полный чек-лист и PostgreSQL-регрессии

Выберите **18 — Run all checks**.

Будут выполнены 16 основных проверок, управляемая сессия и отдельный набор из
8 реальных PostgreSQL-регрессий. Итоговая таблица содержит **18 совпадений**:
последняя строка обозначает всю PostgreSQL-серию, а не один тест.

**Ожидается:** все строки `OK`, коды в столбцах Expected / Actual совпадают.
Результат сохраняется в `checklist.json` текущей папки `run-…`.

Только регрессионная подготовка использует локальное административное подключение,
чтобы создать и убрать временные роли и схему. Она проверяет, в частности,
владельца, FORCE RLS, BYPASSRLS, членство ролей, составление политик и права столбцов.
Обычная диагностика использует стандартное подключение.

Для отдельного запуска этой серии выберите **20 — PostgreSQL regression suite**.
Ожидается `PASS real PostgreSQL inspector integration suite`.

Для полного прогона без меню можно закрыть текущую сессию пунктом 0 и выполнить:

```powershell
.\lab.cmd -Check
```

После возврата приглашения PowerShell отдельно выполните:

```powershell
Write-Host "Код учебной проверки: $LASTEXITCODE"
```

Ожидается 0. `-Check` явно разрешает подготовку только описанной учебной среды.
Не запускайте его одновременно с открытой учебной сессией.

## 9. JSON-отчёт

Выберите **19 — Export JSON replay report**.
В консоли появится путь к `report.json`. Откройте его редактором.

Проверьте:

- `result` равен PASS;
- `http.status` равен 200, `http.row_count` равен 1;
- подтверждённая роль — authenticated;
- есть результаты отдельных проверок и ограничения;
- нет bearer-токена, пароля, DSN, строк документа или текста SQL-предиката.

JSON создаётся самим запускателем в UTF-8. Перенаправление через `>` в старом
PowerShell не требуется. Не сохраняйте и не пересылайте сырой `supabase status`.

## 10. Мастер настройки собственного сценария

Это отдельная проверка мастера init. Завершите учебное меню пунктом **0**.
База остаётся запущенной. В обычном PowerShell выполните:

```powershell
uv run --project python rls-doctor init --interactive --directory .rls-doctor/practice/manual-project
```

Введите значения по очереди:

| Вопрос | Что ввести |
| --- | --- |
| Local API URL | `http://127.0.0.1:55321` |
| Local PostgreSQL port | `55322` |
| Test table | `public.documents` |
| Test identity | `anon` |
| Expected HTTP status | `200` |
| Expected number of rows | `0` |
| Approve this destination… | `y`, после проверки адреса |
| Save configuration… | `y` |

Создаются два файла: `rls-doctor.toml` и `documents.yaml`. Ключи и пароли
не запрашиваются. Повтор той же команды должен вернуть INIT_EXISTS / 3 и
сохранить файлы. Если проходите инструкцию повторно, выберите новую папку,
например `manual-project-2`; удалять существующие файлы не требуется.

Проверка управляемой сессии с этой конфигурацией:

```powershell
uv run --project python rls-doctor session --config .rls-doctor/practice/manual-project/rls-doctor.toml --workdir .rls-doctor/practice
```

Выберите **1**. Ожидается HTTP 200, 0 строк и **UNKNOWN / 2**: мастер намеренно
не включает доверенный пробник роли. Ключи загружены, но исполняемая роль не
подтверждена. Не меняйте этот вывод на PASS вручную. Пункт 0 закрывает сессию.

Этим проверяется, что удобная настройка не превращает отсутствие доказательств
в положительный результат. Подробности — [в руководстве session](managed-session.ru.md).

## 11. Автоматические проверки исходников

После выхода из всех меню можно выполнить по одной команде:

```powershell
pnpm.cmd typecheck
pnpm.cmd lint
pnpm.cmd test
uv run --project python pytest python/tests -m 'not integration' -q
uv run --project python ruff format --check python scripts
uv run --project python ruff check python scripts
```

Каждая команда должна завершиться кодом 0, без failed/error.
Проверка типов Python:

```powershell
Push-Location python
uv run mypy
Pop-Location
```

SDK-тесты проверяют также выключенный по умолчанию захват, сохранность запросов
и ответов, ограничения записи и отсутствие секретов. Python-тесты проверяют
форматы, локальные ограничения, обработку ошибок и отчёты.
Интеграционные тесты в этой pytest-команде исключены: они реально выполняются
отдельно в пунктах 18/20 и не должны считаться пройденными по одному deselected.

## 12. Остановка и повторный запуск

1. Закройте меню пунктом **0**. Если находитесь в меню session, сначала 0 для
   возврата в учебное меню, затем ещё 0 для выхода в PowerShell.
2. Выполните:

```powershell
.\lab.cmd -Stop
```

Останавливается только `rls-doctor-practice`. Данные сохраняются.
Повторный запуск — `.\lab.cmd`; подготовка создаст новую пару тестовых личностей
и снова назначит им восемь синтетических строк.
Не используйте `supabase db reset`, `stop --no-backup` или глобальную очистку Docker
для обычного завершения этого тестирования.

## 13. Что записать при проверке

Достаточно таблицы: номер пункта → ожидалось → получено → MATCH/MISMATCH.
Если есть MISMATCH, сохраните название проверки и безопасный код ошибки.
Не присылайте значения ключей, токенов, паролей или сырой вывод status.

Эта инструкция не подтверждает работу с production, браузерный SDK, операции
записи, автоматическое исправление политик, свежий удалённый CI или установку
на чистом компьютере: такие возможности здесь не проверяются.


## Если лаборатория уже открыта

Ошибка `LAB_SESSION_BUSY` означает, что другая учебная сессия ещё работает
или файл блокировки недоступен. Закройте меню первой сессии пунктом **0**
и повторите запуск. Не удаляйте `.session.lock`: наличие файла нормально,
защита действует через блокировку операционной системы. При закрытии процесса
она освобождается автоматически. Это предотвращает переназначение тестовых
строк другой паре пользователей посреди вашей проверки.
