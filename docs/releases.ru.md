# Релизы

[English](releases.md) · **Русский**

GitHub Release — опубликованный снимок проекта, связанный с Git-тегом. Он сам по себе не публикует пакеты в npm или PyPI. Здесь описан процесс; это изменение документации не создаёт тег или релиз.

## Какую версию выпускать первой

Для первого предварительного выпуска предлагается **v0.1.0-alpha.1** с отметкой pre-release. Это предложенное имя, не существующий релиз. **v0.1.0** лучше использовать после выполнения критериев полного MVP. Alpha может быть снимком исходников с явно перечисленными ограничениями; не называйте его стабильным или полностью проверенным продуктом.

Сейчас версии пакетов в коде — `0.1.0`, как метаданные разработки. Перед сборкой alpha нужно согласованно изменить:

| Место | Alpha | Стабильная версия |
| --- | --- | --- |
| package.json в корне и SDK | 0.1.0-alpha.1 | 0.1.0 |
| Python pyproject.toml и __version__ | 0.1.0a1 | 0.1.0 |
| Git-тег | v0.1.0-alpha.1 | v0.1.0 |

Обновите lock-файлы, примеры и отображаемые версии. В Python и JavaScript обозначения отличаются. Нельзя просто переименовать старый wheel `0.1.0` в alpha. Текущее оформление не меняет версии приложения.

## Что нужно до стабильного выпуска

- Отправить проверенную ветку, создать PR и после ревью/проверок объединить её с main. Главная страница по умолчанию показывает README из main.
- Выполнить команды из [инструкции разработки](development.md), проверить установку wheel.
- Выполнить настоящий Docker/Supabase E2E из [инструкции запуска](getting-started.md). Подмена HTTP-ответов этот этап не заменяет.
- Убедиться, что GitHub Actions прошёл для конкретного коммита будущего тега.
- Получить независимое ревью TypeScript/Python частей, не выдумывая участие второго разработчика.
- Обновить CHANGELOG.md и датированный отчёт проверок; сохранить ограничения совместимости.

## Как создать черновик

1. Откройте **Releases → Draft a new release**.
2. Выберите тег версии и проверенный коммит/ветку.
3. Добавьте название, описание и проверенные сборки, если они нужны.
4. Для alpha включите **This is a pre-release**.
5. Нажмите **Save draft**; публикуйте после проверки содержимого и целевого коммита.

Подготовлены [русский шаблон описания](releases/v0.1.0-alpha.1.ru.md) и [английский вариант](releases/v0.1.0-alpha.1.md). Это локальные заготовки, а не объявления о выходе версии. [Официальная инструкция GitHub](https://docs.github.com/en/repositories/releasing-projects-on-github/managing-releases-in-a-repository?tool=webui).

## Что прикладывать

Для предварительного выпуска исходников могут быть достаточны архивы тега GitHub. Устанавливаемые пакеты собирайте заново из точного исходного коммита; проверьте установку и контрольные суммы. Не загружайте секреты, captures, локальные конфигурации, дампы баз, node_modules, .venv и необработанные логи. SDK пока является private workspace-пакетом; публикация npm требует отдельной подготовки.

CHANGELOG хранит историю версий, Releases — снимки для скачивания, Issues/PR — обсуждение разработки. В следующих релизах указывайте изменения, реальные проверки, ограничения и порядок обновления. Исправления опубликованной версии оформляйте новой версией, не передвигая старые теги.


## Локальная проверка устанавливаемых пакетов

Команда `uv run --project python python scripts/package_check.py` собирает wheel,
исходный Python-архив и SDK-tgz, проверяет лицензии и устанавливает оба компонента
в отдельные окружения. Проверяются файловый sink, типы SDK, версия CLI и общий
контракт события. Путь к архивам, SHA256SUMS и manifest.json выводится в терминал.

Это preview из текущего рабочего дерева, а не публикация. Manifest отмечает
коммит и наличие незакоммиченных изменений. Для реального выпуска пересоберите
пакеты из утверждённого исходного коммита и выполните все проверки релиза.
Не прикладывайте каталог окружений/захватов целиком; используйте список архивов
из manifest.json. Версии не меняются автоматически и SDK остаётся private.
