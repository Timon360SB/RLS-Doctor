# Ручная проверка RLS Doctor: последовательный план

Эта инструкция рассчитана на подготовленную среду в
`C:\Users\sbtim\Documents\GitHub\RLS-Doctor`.

Учебная база использует API 55321 и PostgreSQL 55322. Отдельное приложение
с задачами — 56321 и 56322. Пользователи и строки синтетические. Для ручных
команд подготовлены несекретные файлы `.rls-doctor/manual-review/`; они
исключены из Git. На другом компьютере используйте [независимую приёмку](release-review.ru.md).

Автоматическая предварительная проверка не заменяет ваши действия ниже.
Результаты агента лежат отдельно в `preflight-output`, ваши отчёты будут создаваться
с именами `result-pass.json` и т. п. Не отправляйте всю папку `.rls-doctor`:
для разбора достаточно выбранного очищенного отчёта и номера проверки.

## 1. Открыть меню

Откройте новое окно PowerShell. Выполните команды по очереди:

```powershell
cd C:\Users\sbtim\Documents\GitHub\RLS-Doctor
```

```powershell
.\lab.cmd -Language ru
```

На вопрос о подготовке ответьте **д** или **y**, затем Enter. Дождитесь меню.
Дополнительное окно не должно открываться. До появления меню команду повторно
не запускайте. Ключи и переменные окружения вводить не нужно.

**Пока видно «Выберите проверку» и `>` — вводите только номер пункта.**
Команды PowerShell из следующих разделов выполняются после выхода пунктом **0**,
когда снова видно `PS C:\…>`. Внутреннее меню пункта 17 закрывается своим 0,
после чего для выхода из всей лаборатории нужен ещё один 0.

После каждой проверки меню возвращается. Внизу отчёта сравнивайте
«Ожидалось / Получено» и «СОВПАДАЕТ». Числа 0/1/2/3 — коды результатов,
а не номера следующего действия.

| Результат | Значение |
| --- | --- |
| PASS / 0 | Наблюдение совпало с ожиданием |
| FAIL / 1 | Ожидание нарушено |
| UNKNOWN / 2 | Доказательств для нужного вывода недостаточно |
| ERROR / 3 | Проверка не выполнена или входные данные отклонены |

FAIL/ERROR в специально неправильном примере ожидаемы. Проверка считается
корректной, когда получен именно предусмотренный результат с нужной причиной.

## 2. Пройти отдельные пункты меню

### 1 — Проверка подключения

1. Введите **1**, Enter.
2. Дождитесь отчёта, найдите общий результат и проверки ролей/API.
3. Ожидается **PASS / 0**, внизу — совпадение.

Это подтверждает работу учебного API, базы и подготовленной проверки роли.
Если здесь ERROR, сначала разберите его; последующие пункты пока не считайте проверенными.

### 2 — Захват запроса SDK и проверка события

1. Введите **2**, Enter.
2. Найдите PASS и успешную проверку формата события.
3. Ожидается **PASS / 0**.

Настоящий клиент Supabase выполняет запрос, SDK создаёт очищенное событие,
Python принимает его по общей схеме. В текущей папке `run-…` создаётся event.json.
Его путь не нужно переносить в команды: для отдельных проверок ниже уже есть стабильная копия.

### 3 — Офлайн-анализ

1. Введите **3**, Enter.
2. Прочитайте ограничения подтверждения личности.
3. Ожидается **UNKNOWN / 2**, при этом пример должен совпасть с ожиданием.

Наличие заголовка авторизации в событии не доказывает, от чьего имени база выполнила
исходный запрос. UNKNOWN здесь сохраняет эту неопределённость.

### 4 — Алиса видит только свою запись

1. Введите **4**, Enter.
2. Проверьте HTTP 200 и одну строку.
3. Найдите успешные проверки наличия своей и отсутствия чужой записи.

Ожидается **PASS / 0**, роль authenticated. Одного количества недостаточно:
важно, что вернулась нужная запись.

### 5 — Боб видит только свою запись

1. Введите **5**, Enter.
2. Проверьте HTTP 200, одну строку и успешное исключение чужой записи.
3. Ожидается **PASS / 0**.

Проверяем ту же границу доступа с противоположной стороны: теперь своя запись — Боба.

### 6 — Нет ожидаемой авторизации

1. Введите **6**, Enter.
2. Найдите анонимную роль anon, HTTP 200 и ноль строк.
3. Ожидается **FAIL / 1** и совпадение учебного результата.

Запрос отправлен анонимно, хотя сценарий ожидал доступ авторизованного пользователя.
Инструмент должен обнаружить расхождение.

### 7 — Нет разрешающей политики

1. Введите **7**, Enter.
2. Проверьте HTTP 200, ноль строк и сведения о политиках.
3. Ожидается **FAIL / 1**.

Обычное право SELECT выдано, но подходящей разрешающей RLS-политики нет.
Это отдельный случай от отсутствия права чтения.

### 8 — Ожидаемый отказ в чтении

1. Введите **8**, Enter.
2. Найдите HTTP 403 и класс ошибки permission.
3. Ожидается **PASS / 0**.

Сценарий заранее ожидает отказ, потому что SELECT не выдан. PASS означает,
что ожидаемый запрет подтвердился. Политика RLS сама не выдаёт SQL-привилегии.

### 9 — Обнаружение чужой записи

1. Введите **9**, Enter.
2. Найдите HTTP 200, две строки и нарушенную проверку исключения чужой записи.
3. Ожидается **FAIL / 1**.

В этой тестовой таблице намеренно неправильная политика. FAIL показывает,
что инструмент заметил утечку, а не пропустил её как нормальный ответ.

### 10 — Пустой ответ без доказанной причины

1. Введите **10**, Enter.
2. Проверьте HTTP 200 и ноль строк.
3. Найдите EMPTY_RESULT_AMBIGUOUS / UNVERIFIED.

Ожидается **PASS / 0**: отсутствие строки было ожидаемо, но причина пустого
ответа не объявляется доказанным запретом RLS.

### 11 — Отсутствует право SELECT

1. Введите **11**, Enter.
2. Найдите SELECT_PRIVILEGE_MISSING и сведения о правах.
3. Ожидается **UNKNOWN / 2**.

Инспектор подтвердил факт конфигурации, но сам по каталогам не устанавливает,
какие строки увидел бы произвольный запрос приложения.

### 12 — Неверный токен

1. Введите **12**, Enter.
2. Проверьте код INVALID_TEST_TOKEN.
3. Ожидается **ERROR / 3**.

Неподходящая тестовая авторизация должна отклоняться до чтения таблицы.

### 13 — Неподдерживаемое событие

1. Введите **13**, Enter.
2. Проверьте INVALID_EVENT.
3. Ожидается **ERROR / 3**.

Инструмент должен отказать событию с неподдерживаемой версией схемы.

### 14 — Нет разрешения на локальный запуск

1. Введите **14**, Enter.
2. Проверьте LOCAL_APPROVAL_REQUIRED.
3. Ожидается **ERROR / 3**.

Даже локальный адрес должен быть явно разрешён конфигурацией.

### 15 — Удалённый адрес

1. Введите **15**, Enter.
2. Проверьте UNSAFE_ENDPOINT.
3. Ожидается **ERROR / 3**.

Сценарий с удалённым адресом отклоняется. Рабочая конфигурация лаборатории сохраняется.

### 16 — Попытка PATCH

1. Введите **16**, Enter.
2. Проверьте INVALID_SCENARIO.
3. Ожидается **ERROR / 3**.

Воспроизведение первой версии поддерживает чтение, поэтому сценарий изменения данных не принимается.

### 17 — Управляемая сессия

1. Введите **17**, Enter — откроется второе меню в том же окне.
2. Внутри введите **1**: ожидается успешное выполнение подготовленного сценария.
3. Внутри введите **2**: появятся настройки таблицы; общий вывод о runtime остаётся UNKNOWN.
4. Введите **0**, чтобы вернуться в основное меню.

Проверяется работа без копирования ключей. Не закрывайте всё окно, чтобы вернуться из подменю.

### 18 — Полный чек-лист

1. В основном меню введите **18**, Enter.
2. Дождитесь завершения всех проверок.
3. Во всех 18 строках столбец «Совпадает» должен содержать **Да**.

Здесь также выполняются восемь настоящих PostgreSQL-регрессий. FAIL/ERROR отдельных
преднамеренных примеров не являются ошибкой чек-листа, если ожидание совпало.

### 19 — Сохранение отчёта из меню

1. Введите **19**, Enter.
2. Скопируйте напечатанный путь к report.json и откройте файл редактором.
3. Проверьте result PASS, http.status 200, http.row_count 1 и подтверждённую роль authenticated.

В файле должны быть результаты проверок и ограничения, без ключей, паролей
и текста документов. Новый --output и защиту существующего файла проверяем отдельно ниже.

### 20 — Проверки поведения PostgreSQL отдельно

1. Введите **20**, Enter.
2. Дождитесь сообщения PASS о регрессионных тестах инспектора.

Проверяются роли, владелец, обход RLS, FORCE RLS, политики и права столбцов.
Подготовка этой серии создаёт/удаляет временные роли и схему только в учебной базе.

## 3. Проверить CLI и экспорт с постоянными путями

Сначала выйдите из основного меню пунктом **0**. Базу пока не останавливайте.
Следующие команды вводятся в обычный PowerShell из корня репозитория.
Имена выходных файлов ниже свободны для первого ручного прогона. При повторе
используйте новые имена с суффиксом -2, -3 и т. п.; старые отчёты не удаляйте.
Исключение — пункт 25, где повтор того же имени специально проверяет запрет перезаписи.

После проверяемой команды можно отдельно выполнить:

```powershell
Write-Host "Код проверки: $LASTEXITCODE"
```

Делайте это сразу после команды, до запуска редактора или другой программы.

### 21 — Справка и версия

Выполните по очереди:

```powershell
uv run --project python rls-doctor --version
uv run --project python rls-doctor --help
```

Ожидаются версия сборки и перечень команд. Это проверяет обычную точку запуска,
а не только обёртку лаборатории.

### 22 — Проверить подготовленное событие и сохранить JSON

```powershell
uv run --project python rls-doctor validate .rls-doctor/manual-review/event.json --format json --output .rls-doctor/manual-review/validation-manual.json
```

Ожидается **PASS / 0** и чистый JSON в терминале. Откройте validation-manual.json
в `.rls-doctor/manual-review/`: результат должен совпадать с терминалом.
Событие было получено настоящим SDK при подготовке; эта команда лишь проверяет его файл.

### 23 — Проанализировать то же событие без базы

```powershell
uv run --project python rls-doctor analyze .rls-doctor/manual-review/event.json --expected-role authenticated --language ru
```

Ожидается **UNKNOWN / 2**. Найдите объяснение, что заголовок авторизации не
подтверждает личность и роль исходного запроса.

### 24 — Получить PASS через обычный session

```powershell
uv run --project python rls-doctor session --run --config .rls-doctor/manual-review/rls-doctor.toml --workdir .rls-doctor/practice --language ru --output .rls-doctor/manual-review/result-pass.json
```

Ожидается **PASS / 0**, HTTP 200, ноль строк, подтверждённая роль anon.
Это отдельный сценарий: анонимный клиент и должен получить ноль документов.
Ключи сессия получает сама. В result-pass.json найдите run_id и запомните его.

### 25 — Защита существующего отчёта

Повторите **в точности команду пункта 24** с тем же result-pass.json.
Ожидается **ERROR / 3, REPORT_EXISTS**. Откройте прежний файл:
его run_id и прежний PASS должны сохраниться. Для повторного успешного прогона
выберите другое имя, например result-pass-2.json; удалять старый файл не нужно.

### 26 — Получить ожидаемый FAIL

```powershell
uv run --project python rls-doctor session --run --config .rls-doctor/manual-review/rls-doctor.toml --workdir .rls-doctor/practice --scenario .rls-doctor/manual-review/mismatch.yaml --language ru --output .rls-doctor/manual-review/result-fail.json
```

Ожидается **FAIL / 1**: намеренно ожидается одна строка, а анонимный клиент
получает ноль. В отчёте должна нарушиться проверка количества.

### 27 — Получить ожидаемый UNKNOWN

```powershell
uv run --project python rls-doctor session --run --config .rls-doctor/manual-review/unknown.toml --workdir .rls-doctor/practice --language ru --output .rls-doctor/manual-review/result-unknown.json
```

Ожидается **UNKNOWN / 2** при HTTP 200 и нуле строк. Пробник роли отключён
конфигурацией, поэтому исполняемая роль не объявляется подтверждённой.

### 28 — Получить ожидаемый ERROR

```powershell
uv run --project python rls-doctor session --run --config .rls-doctor/manual-review/disabled.toml --workdir .rls-doctor/practice --language ru --output .rls-doctor/manual-review/result-error.json
```

Ожидается **ERROR / 3, LOCAL_APPROVAL_REQUIRED**. Адрес не одобрен этой
намеренно отключённой конфигурацией. Откройте result-error.json: должна быть
именно эта причина, а не произвольная ошибка подключения.

### 29 — Отклонить неправильное событие обычной CLI

```powershell
uv run --project python rls-doctor validate .rls-doctor/manual-review/invalid-event.json --language ru
```

Ожидается **ERROR / 3, INVALID_EVENT**. Исправлять этот специально неправильный файл не нужно.

## 4. Проверить мастер настройки

### 30 — Создать собственную конфигурацию через вопросы

```powershell
uv run --project python rls-doctor init --interactive --directory .rls-doctor/manual-review/wizard-check --language ru
```

| Вопрос | Что ввести |
| --- | --- |
| Адрес API | `http://127.0.0.1:55321` |
| Порт PostgreSQL | Сначала `abc`, убедитесь, что вопрос повторился; затем `55322` |
| Таблица | `public.documents` |
| Личность | `anon` |
| HTTP-статус | `200` |
| Число строк | `0` |
| Разрешение выбранного адреса | `y` после проверки адреса |
| Сохранение | `y` |

Ожидаются два новых файла. Ошибка порта не должна сбросить правильный адрес API.
Если wizard-check уже существует после вашего прошлого прогона, используйте wizard-check-2.

Дополнительно можно проверить отмену: запустите тот же мастер с новым каталогом
`wizard-cancel` и на первом вопросе нажмите Ctrl+C. Ожидается сообщение об отмене,
код 0 и отсутствие новых файлов конфигурации. Это не означает успешный тест доступа:
вы отменили только настройку.

### 31 — Убедиться, что мастер не перезаписывает файлы

Повторите команду пункта 30 с тем же каталогом. Ожидается **ERROR / 3, INIT_EXISTS**
до повторных вопросов. Прежние файлы должны остаться на месте.

### 32 — Запустить созданную конфигурацию

```powershell
uv run --project python rls-doctor session --run --config .rls-doctor/manual-review/wizard-check/rls-doctor.toml --workdir .rls-doctor/practice --language ru
```

Ожидается **UNKNOWN / 2**, HTTP 200, ноль строк. Мастер по умолчанию не включает
доверенный пробник роли. Если использовали wizard-check-2, измените путь соответственно.

## 5. Проверить установленный продукт на другом примере

```powershell
uv run --project python python scripts/task_board_check.py --check
```

1. Дождитесь сборки и установки пакетов; команду повторно не запускайте.

## 6. Язык, перезапуск и остановка

### 34 — Английский интерфейс по умолчанию

Запустите `.\lab.cmd` без языкового параметра, ответьте y, выберите **1**.
Ожидаются английское меню и PASS. Затем выйдите **0**. При желании сравните
с `.\lab.cmd -Language ru`; коды и смысл результатов должны совпадать.

### 35 — Остановка и повторный запуск

В обычном PowerShell:

```powershell
.\lab.cmd -Stop
.\lab.cmd -Language ru
```

Команды выполняются по очереди. После второго запуска подтвердите подготовку,
выберите **1**, затем **4**: ожидаются PASS и одна своя запись. Данные сохраняются,
подготовка назначает тестовые строки новой паре пользователей. Выйдите **0**.

### 36 — Завершить работу

```powershell
.\lab.cmd -Stop
uv run --project python python scripts/task_board_check.py --stop
```

Останавливаются лаборатория и приложение с задачами, их данные сохраняются.
Если использовали прежний demo.cmd, остановите его отдельно: `.\demo.cmd -Stop`.
Эти команды не закрывают Docker Desktop целиком.

## Как сообщить об ошибке

Пришлите номер пункта, что ввели, что ожидали и что получили. Для меню полезна
строка «Ожидалось / Получено»; для CLI — result и фиксированный код ошибки.
Не присылайте ключи, пароли, токены, дамп переменных окружения и сырой supabase status.

Если окно закрыли — откройте новое PowerShell, перейдите в репозиторий и снова
запустите lab.cmd. При долгой паузе и ошибке истёкшего токена перезапустите меню:
будет подготовлена новая тестовая пара. Постоянные анонимные сценарии раздела 3
не требуют сохранённого пользовательского токена.
